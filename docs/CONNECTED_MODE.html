用户输入 两个协议 三个 Use Cases
Refactor · Phase 4

登录一次，三个 tab 都能用。

重构后，用户不再需要上传 PBIP zip、PDF，也不再需要填 XMLA URL。一次 Microsoft 登录 + 两个下拉选择，三个 use case 共享同一个 connection context。本文说明用户输入方式和 Power BI Service 两个协议如何分别服务这三个 use case。

01 · 用户输入

用户要做的事，就这 5 步。

之前的"上传 zip + 上传 PDF + 填 URL + 配 exe + 选认证方式"全部消失。重构后的输入流程一共不到 30 秒，而且大部分时间在等 Microsoft 登录确认。

重构后的 Sidebar 长这样

PowerBI Assistant ───────────────────────────────── Anthropic API Key sk-ant-........... Output language English ▾ ─ Power BI Connection ─────────── Sign in with Microsoft ← 未登录时显示 Signed in as alice@contoso.com ← 登录后显示 Workspace: Sales Analytics ▾ Report: Q3 Revenue Dashboard ▾ Dataset: Q3 Revenue (auto) Status: ● Connected · Fabric

认证机制

登录走的是 MSAL Device Code Flow：用户点击登录后，应用显示一串验证码，用户在浏览器里输入这串码并用 Microsoft 账号登录。不需要在 Azure AD 里注册 redirect URI，也不需要 client secret，所以部署到任何环境都一样使用。Token 自动缓存在 session 里，刷新页面不会丢失登录状态；token 过期了 MSAL 自动 refresh。

02 · 两个协议

Power BI Service 暴露两扇门。

用户登录后拿到的那一个 OAuth access token，同时打开 Power BI Service 的两个通道：REST API 和 XMLA Endpoint。它们是互补的 —— 一个负责 metadata 和文件级操作，一个负责语义模型和实时查询。

Microsoft Entra IDOAuth 2.0 · MSAL Device Code Flow
access_token
Power BI REST APIHTTPS · JSON
XMLA EndpointTDS / SOAP · via MCP
Channel A

Power BI REST API

HTTPS · JSON · api.powerbi.com/v1.0/myorg
  • 列出用户有权限的 workspaces
  • 列出 workspace 里的 reports 和 datasets
  • 拿一个 report 的 定义（page / visual 结构，相当于 report.json）
  • 把一个 report 导出成 PDF / PPTX / PNG（async job + 轮询）
  • 下载 PBIP 整包（用于 README 写回路径）
Channel B

XMLA Endpoint

TDS / SOAP · powerbi://api.fabric.microsoft.com/...
  • 完整的 语义模型（tables / columns / relationships）
  • 所有 measures 和它们的 DAX 表达式
  • Partitions（M 代码 / DirectQuery SQL / 数据源）
  • 执行任意 DAX 查询（包括 DMV 元数据查询）
  • 安全角色 / KPI / Hierarchies

关键点：同一个 token 打开两扇门

用户只登录一次。OAuth scope 用 https://analysis.windows.net/powerbi/api/.default，这个 scope 既覆盖 REST API 也覆盖 XMLA。**XMLA 通过既有的 Power BI Modeling MCP Server 调用**（Chat tab 现在用的就是它），重构后只是把它从"只给 Chat 用"扩展到"三个 tab 共享"。

注意：XMLA 有 license 门槛

XMLA endpoint 只对以下三种 license 开放：Premium Per User (PPU)、workspace 在 Premium capacity (P SKU) 上、workspace 在 Fabric capacity (F SKU) 上。普通 Pro 用户的 workspace 没有 XMLA。这是重构后明确接受的约束 —— 不满足条件的用户无法使用本应用。

每个 use case 的协议组合

01

Documentation

Sonnet 4.6 · 输出 Markdown

生成完整的报表文档。需要同时拿到报表结构（每页有哪些 visual、绑了什么字段）和语义模型（有哪些 table、measure 是怎么算的、数据源是什么）。两扇门都要用。

REST API 拿什么
  • 报表的 page / section 列表
  • 每个 page 下的 visual 定义（type、projection、绑定字段）
  • page 级别和 visual 级别的 filter
XMLA 拿什么
  • 所有 table 的名字和 columns
  • 所有 measure 的名字 + DAX 表达式 + 描述
  • 所有 partition 的 M 代码（数据源）
  • 表之间的 relationships
02

README

Sonnet 4.6 多模态 · 注入 README 页面

给报表内部加一页 README。Claude 需要看每页长什么样（视觉印象）+ 每页的 visual 结构定义（精确字段名）—— 两者结合才能写出又准确又有视觉印象的 README。这是个纯 REST API 的 use case，XMLA 不参与。

REST API 拿什么
  • Get Report Definition: report 的 page / visual 结构
  • ExportTo: 把整个报表导成 PDF（async 任务 + 轮询拿结果）
  • PDF 在内存里被 PyMuPDF 转成每页 PNG，喂给多模态 Claude
  • Export: 下载原始 PBIP zip，用于本地注入 README 节点后给用户下载
XMLA
  • 不使用。README 只关心视觉层的展示，不需要 dataset 层的信息。
03

Chat

Haiku 4.5 · tool-use loop

用户用自然语言对着实时模型问问题。Claude Haiku 4.5 通过既有的 Power BI Modeling MCP Server 反复 call tool，每次都是直接打到 XMLA endpoint。这是个几乎全 XMLA 的 use case —— REST 只在最开始用了一下，用来列 workspaces / reports 和派生 XMLA URL。

REST API 拿什么
  • 列出 workspace / report，给用户选
  • 根据 workspace 名拼出 powerbi://... 的 XMLA URL
  • 对话开始后，不再被调用
XMLA 拿什么
  • 通过 MCP 暴露的 7 个只读 tool 给 Claude 用
  • Claude 决定调用哪个 tool（比如 measure_operations）
  • 实时跑 DAX 查询（dax_query_operations）拿真实数据
  • 整个 tool-use loop 在 MCP session 里跑，最多 6 轮迭代

一句话总结

REST API 管"文件和结构"，XMLA 管"模型和查询"。Documentation 两个都要、README 只要 REST、Chat 几乎全是 XMLA。但所有的协议调用都由同一个 OAuth token 授权 —— 用户只登录一次。
